In Brief

Editorial #1 argued that the implementation, not the vendor, is the real unit of trust. This piece asks what happens after approval. Traditional TPRM treats trust as a point-in-time decision - assess, approve, monitor, reassess - but AI implementations keep changing after they're approved: permissions expand, integrations evolve, capabilities increase. The vendor can stay exactly the same while the risk profile of the implementation changes completely. This piece introduces the Continuous Trust Loop, and argues that the goal isn't monitoring everything - it's continuously knowing what actually changes the trust decision.

Approval Is Not Trust

Traditional TPRM treats trust as a point-in-time decision

In my first editorial, I argued that the implementation - not the vendor alone - should become the unit of trust. That leads to the next question: what happens after approval?

Traditional TPRM runs on a simple sequence: Assess → Approve → Monitor → Reassess. But AI implementations don't stay still. Permissions expand. Data access changes. Integrations evolve. Capabilities increase. Business usage shifts. The vendor may remain unchanged while the risk profile of the implementation changes significantly.

Approval establishes a trust boundary. It does not guarantee that the boundary will remain intact.
From Monitoring to Continuous Trust

Continuous monitoring isn't a new concept. Turning it into a trust decision is.

The challenge is turning monitoring into an actual trust decision capability. The future model should look more like: Assess → Approve → Observe → Detect → Reassess → Adapt. I call this the Continuous Trust Loop.

The objective isn't to monitor everything. It's to continuously know what changed, and whether it still matters.

Trust should not be a snapshot of the implementation. It should be a continuously maintained understanding of it.

Not Every Change Should Trigger Reassessment

This is where the operating model becomes practical

If every configuration change triggers a new TPRM assessment, organizations simply create more bureaucracy. Instead, organizations should define risk-significant changes in advance - the ones that can actually change the decision.

Here's the pattern most software organizations will recognize. An engineering team approves an AI coding assistant to autocomplete code and answer questions against public documentation - low risk, easy approval. Six months later, that same assistant is connected to the private source repositories, wired into the CI/CD pipeline, and has permission to open pull requests directly against production branches. Nobody re-ran the risk assessment, because nobody "installed a new vendor." The contract didn't change. The invoice didn't change.

The vendor hasn't changed. But the implementation has materially changed. That should change the trust decision.
Where Agents Can Help

Agentic capabilities are particularly interesting here

Agents can continuously maintain implementation context, correlate signals across systems, detect meaningful changes, and surface situations that warrant reassessment. Going back to the coding-assistant example - an agent watching for exactly this pattern could have flagged the moment the assistant's permissions expanded from "read public docs" to "write access on production branches," and surfaced it as a reassessment trigger before the next release, not during the next annual review.

Note

The goal isn't autonomous risk acceptance. It is machine-speed context and human judgment.

Three Moves to Start Building Continuous Trust

Organizations don't need to rebuild TPRM overnight

1. Capture context. At approval, document more than the vendor - intended use, data, permissions, capabilities, integrations, and business criticality. This is what lets you later distinguish normal evolution from changes that materially alter risk.

2. Define risk-significant change. Agree in advance which changes could materially alter the implementation's risk profile and should trigger reassessment. Not every change matters - the goal is knowing which ones can change the decision.

3. Establish continuous trust signals. Combine vendor intelligence with implementation, access, capability, and usage signals.

Questions for Leaders

Sit with these before your next vendor review

  1. What changes in an AI implementation should trigger reassessment?
  2. Can you distinguish routine changes from risk-significant changes?
  3. If an implementation changed tomorrow, would your TPRM program know?
